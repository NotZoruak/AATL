# 更新数据任务设计

## 1. 目标

新增「更新数据」任务，按用户选择依次自动识别并保存仓库数据、刀帐数据。任务支持每次、每天、每周三种触发频率，并通过独立的 `UpdateData` Entry 作为任务身份。

更新数据任务不依赖用户手动打开仓库或刀帐页面。任务从当前游戏画面进入自己的主枢纽，由主枢纽处理闪退恢复、公告、登录、更新、断线和其他意外页面，再根据识别内容执行对应流程。

## 2. 任务配置

任务注册在 `assets/interface.json`：

- 名称：`更新数据`
- Entry：`UpdateData`
- 选项：`识别内容`
- `识别内容` 为下拉框，选项为「仓库」「刀帐」「仓库+刀帐」
- 增加频率下拉框，选项为「每次」「每天」「每周」

「仓库+刀帐」固定按“仓库 → 回本丸 → 刀帐”的顺序执行。识别成功后自动保存正式数据；某一部分失败时保留该部分已有数据，不因另一部分成功而覆盖失败部分。

## 3. 主枢纽

### 3.1 更新数据主枢纽

新增 `UD_DetectWhereAmI`。其结构以 `U_DetectWhereAmI` 为基础，使用 `UD_` 前缀复制完整的通用恢复链和异常处理链：

- `UD_LeaveTroopRecord`
- `UD_IsAnnouncementPopup`
- `UD_IsAdvertisementPopup`
- `UD_IsTrainingLetter`
- `UD_IsLoginReward`
- `UD_IsGameIcon`
- `UD_IsLoginButton`
- `UD_IsGameUpdatePopup`
- `UD_IsInGameUpdatePopup`
- `UD_IsInternalReport`
- `UD_IsConnectionInterrupted`
- `UD_FallbackWait`
- `UD_RestartGame`

主枢纽的 `timeout` 为 `120000`，`on_error` 指向 `UD_RestartGame`。所有通用恢复 node 的回流目标均为 `UD_DetectWhereAmI`，不能直接回流其他任务的主枢纽。

### 3.2 本丸三次确认

更新数据首次进入仓库阶段前，必须连续三次确认位于本丸：

`UD_CheckHomeBrightness → UD_IsHome`

每次成功识别本丸后硬等待 1 秒，再进入下一次确认。任意一次未识别到本丸，都重新从第一次确认开始计数。第三次确认成功后，才进入仓库识别或其他业务阶段。

## 4. 仓库流程

仓库阶段复用现有 `Warehouse_Start` 及仓库扫描动作。仓库扫描完成后进入更新数据专用回本丸枢纽：

1. 在 `[1234,9,37,38]` OCR 识别 `×`、`x` 或 `X`。
2. 命中后点击识别区域。
3. 对 `[1234,9,37,38]` 进行 500ms 冻结等待。
4. 返回回本丸枢纽继续识别。
5. 直到识别不到关闭按钮，确认已回到本丸。

「仓库」模式在此结束；「仓库+刀帐」模式从这里进入刀帐识别枢纽。

## 5. 刀帐识别枢纽

刀帐识别使用独立的 `UD_SwordBookDetectWhereAmI` 枢纽。该枢纽拥有自己的 `UD_SB_` 前缀恢复链，所有异常和通用处理流程回到刀帐枢纽本身，避免恢复后跳回仓库主流程。

### 5.1 进入刀剑男士页面

在本丸状态下：

`UD_SB_CheckHomeBrightness → UD_SB_IsHome`

识别 `[2,163,104,28]` 中的「刀剑男士」并点击，点击后回到刀帐枢纽继续识别。

### 5.2 刀帐页面导航

刀帐枢纽包含以下页面处理：

- OCR `[534,2,220,46]` 识别「刀剑男士一览」；命中后点击 `[10,571,26,80]`，回到刀帐枢纽。
- OCR `[600,7,91,42]` 识别「刀帐」；随后在 `[140,98,4,5]` 进行颜色匹配 `[178,33,32]`。
  - 颜色命中：点击 `[154,161,106,206]`，回到刀帐枢纽。
  - 颜色未命中：点击 `[140,98,4,5]`，冻结该区域 500ms，再回到刀帐枢纽。
- OCR `[527,3,229,43]` 识别「序号」；命中后启动现有 `SwordBookScanAction`。

刀帐识别动作完成后，点击 `[134,5,36,38]`，任务结束。

## 6. 频率与保存

频率判断以 `UpdateData` 为稳定身份保存最近一次成功完成的时间：

- 每次：每次任务队列启动都执行。
- 每天：本地日期变化后首次启动时执行，当天再次启动跳过。
- 每周：本地周变化后首次启动时执行，本周再次启动跳过。

只有对应识别内容全部成功完成后才更新频率记录。跳过时记录明确日志，不启动游戏识别流程。

仓库和刀帐的数据保存由更新数据任务直接完成，不经过页面上的待确认草稿流程。识别失败、停止或中断时，不覆盖该部分正式数据。

## 7. 日志与错误处理

任务日志使用稳定字段：

`[entry=UpdateData]`

业务日志继续保留「仓库识别」「刀帐」等可读前缀。工作记录解析只依赖 `UpdateData`，不依赖任务显示名称、备注或 `label`。

失败处理规则：

- 主枢纽识别超时：执行 `UD_RestartGame`。
- 仓库识别失败：保留仓库旧数据，任务记录仓库阶段失败。
- 刀帐识别失败：保留刀帐旧数据，任务记录刀帐阶段失败。
- 组合模式中单阶段失败：继续执行已定义的安全收尾流程，不把失败阶段标记为成功。
- 用户停止任务：不更新对应频率记录。

## 8. 实现范围

预计修改：

- `assets/interface.json`：注册任务与选项。
- `assets/resource/base/pipeline/UpdateData.json`：主枢纽、回本丸流程、刀帐导航与识别流程。
- `assets/resource/base/custom/`：必要时增加自动保存或阶段调度 custom action。
- `_src/MFAAvalonia/`：频率配置、任务参数处理、自动保存和日志/工作记录接入。
- `_src/MFAAvalonia.Tests/`：选项解析、频率判断、阶段成功/失败和任务身份测试。
- `docs/复用节点清单.md`：补充更新数据枢纽及流水线数量统计。
- `docs/开发日志.md` 与对应版本公告：记录用户可感知的功能变化。

仓库与刀帐现有页面的手动识别、编辑和保存行为保持不变。

## 9. 验收标准

1. 任务列表显示「更新数据」，选项名称显示「识别内容」。
2. 三种识别内容选择均按预期执行。
3. 仓库+刀帐严格按仓库、回本丸、刀帐顺序执行。
4. 主枢纽连续三次确认本丸，每次确认后等待 1 秒。
5. 回本丸流程会持续点击关闭按钮，直到按钮消失。
6. 刀帐页面导航的 OCR、颜色匹配和点击坐标按设计执行。
7. 每天和每周频率不会重复执行，成功后才更新记录。
8. 识别失败不会覆盖对应的旧数据。
9. 所有恢复路径回到正确的更新数据枢纽。
10. 自动化测试通过，资源 JSON 校验通过，发布包包含新资源。
